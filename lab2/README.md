# Лабораторная 2 — Minecraft DSS

Консольная система поддержки принятия решений рекомендует источники предметов
из **существующей базы знаний `lab1/knowledge_base.pl`**. Реализация использует
SWI-Prolog напрямую, без Python-моста, ML, внешних сервисов или копии фактов.

## Запуск

Установите SWI-Prolog 9.x, затем из корня репозитория:

```sh
swipl -q -s lab2/run.pl
```

Начните диалог:

```text
item=шерсть
Какое измерение? overworld / nether / end / any
overworld
Какой способ? mob / structure / any
mob
```

Результат: `mob sheep; биом plains; измерение overworld`, с цепочкой
`drops(sheep, white_wool), spawns(sheep, plains), locates(plains, overworld)`.
Для выхода введите `exit` или завершите поток ввода.

## Формат запроса

`item=<предмет>[;dimension=<измерение>][;method=<способ>]`

Порядок полей произвольный, повторы и неизвестные ключи запрещены. Парсер
проверяет всю строку. `item` обязателен; отсутствующие параметры уточняются
одним или двумя вопросами. Если заданы все поля, рекомендация выдаётся сразу.
Регистр значений не учитывается, пробелы вокруг полей и `=` допускаются.

| Поле | Значения |
| --- | --- |
| item | Идентификатор известного предмета из ЛР1 либо русский синоним |
| dimension | overworld / nether / end / any; обычный мир / ад / энд / любое |
| method | mob / structure / any; мобы / структуры / любой |

Синонимы предметов: шерсть, морковь, панцирь шалкера, золотой шлем,
сырая курятина, сырая баранина. Остальные известные предметы вводятся
идентификаторами Prolog: например, `iron_sword`, `stick`, `rotten_flesh`.

## Как работает вывод

1. Строка разбирается в типизированные слоты и нормализуется по словарям.
2. Диалог дополняет отсутствующие измерение и способ.
3. `recommend/4` вызывает `source/5`, который использует факты и правила ЛР1:
   `item_dimension_from_mob/2` и `item_dimension_from_structure/2`.
4. Измерение и способ — жёсткие фильтры. Результаты сортируются, дубликаты
   удаляются. Ранжирование по качеству не вводится: БЗ не содержит стоимости,
   расстояния и вероятности получения, поэтому все совпадения равноправны.
5. Для каждого источника выводится цепочка исходных фактов.

## Проверяемые сценарии

| Вход (после уточнений) | Результат |
| --- | --- |
| item=white_wool;dimension=overworld;method=mob | sheep → plains → overworld |
| item=carrot;dimension=overworld;method=structure | village → plains → overworld |
| item=shulker_shell;dimension=end;method=any | end_city → end_highlands → end |
| item=golden_helmet;dimension=any;method=structure | mansion → dark_forest → overworld |
| item=raw_chicken;dimension=overworld;method=mob | chicken → plains → overworld |
| item=carrot;dimension=end;method=mob | Нет совпадений; village показана отдельно как альтернатива |
| item=iron_sword;dimension=any;method=any | Предмет известен, место получения/рецепт не описаны |
| item=diamond | Ошибка неизвестного предмета; можно повторить запрос |

Альтернативы при пустом результате **не удовлетворяют исходным ограничениям**
и явно показываются отдельно. Ограничения автоматически не ослабляются.
Сведения о структурах означают наличие отношения `contains/2` в учебной БЗ,
а не гарантированный лут. Система не дополняет модель догадками о Minecraft.
Крафт не рекомендует: в ЛР1 есть `crafted/1`, но нет рецептов.

## Тестирование

```sh
swipl -q -s lab2/tests/dss_tests.pl
python3 lab2/tests/test_cli.py
swipl -q -s lab1/prolog/test/run_tests.pl
```

19 Prolog-тестов проверяют реальные ответы, фильтры, синонимы, грамматику,
дубликаты, пустой/неизвестный ввод и попытку внедрения Prolog-кода.
6 интеграционных тестов запускают настоящий CLI: два уточнения, повтор ввода,
конфликт условий, восстановление после ошибки, EOF и выход с пробелами. Python 3 нужен только
для этих тестов. GitHub Actions запускает обе группы при изменении БЗ/DSS.

## Файлы

- `dss.pl` — разбор, диалог, логические запросы и объяснения.
- `run.pl` — точка входа.
- `tests/` — модульные и интеграционные проверки.
- `examples.txt` — фактический вывод демонстрационных запусков.
- [report.pdf](report.pdf) — общий отчёт по модулю: ЛР1 и ЛР2.

Вторая лабораторная использует вариант **БЗ Prolog**, разрешённый ТЗ.
Сравнение с OWL приведено в отчёте; онтологический backend не заявляется.
